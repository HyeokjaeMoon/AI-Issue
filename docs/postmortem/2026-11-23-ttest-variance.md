# 부검: v0.1.0 t-검정 p-value 오류

> ⚠️ 학습용으로 만든 **가상 사례**입니다.

| 항목 | 내용 |
|---|---|
| 발생 | 2026-11-23 10:20 (v0.1.0 릴리스 다음 날) |
| 해결 | 2026-11-23 16:40 (v0.1.1 배포) |
| 영향 | `ttest_paired()`를 쓴 모든 분석. p-value가 실제보다 작게 나와서, **유의하지 않은 결과가 유의하다고 판정**될 수 있었다. |
| 심각도 | 높음. 계산은 에러 없이 끝나고 결과만 틀리기 때문에 사용자가 알아차리기 어렵다. |

## What — 무슨 일이 있었나
"같은 데이터인데 `scipy.stats.ttest_rel`과 p-value가 다르다"는 사용자 이슈가 올라왔다.

| 시각 | 내용 |
|---|---|
| 10:20 | 사용자 이슈 접수 |
| 10:50 | 재현 성공: `ttest_paired([1,2,3,4],[2,2,4,5])`의 p-value가 scipy와 다름 |
| 11:30 | 원인 확인: `hypothesis.py` 안의 `_std()`가 `np.std(d)`(ddof=0)를 사용 |
| 12:00 | README에 "v0.1.0의 `ttest_paired` 사용 중지" 공지 |
| 15:10 | 수정 PR 머지 |
| 16:40 | v0.1.1 릴리스 |

## Why — 왜 일어났나 (5 Whys)
1. **왜 p-value가 작게 나왔나?** → 표준편차를 n으로 나눠서(ddof=0) 실제보다 작게 계산했다. 그만큼 t 통계량이 커졌다.
2. **왜 ddof=0이었나?** → `hypothesis.py`에 표준편차를 계산하는 `_std()`가 따로 있었고, numpy 기본값을 그대로 썼다.
3. **왜 따로 있었나?** → #8 작업 중에 #7이 고쳐지기 전의 `variance()` 코드를 복사해 왔다. 그런데 #7 수정은 `descriptive.py`만 고쳤다.
4. **왜 테스트가 못 잡았나?** → `ttest_paired` 테스트가 **직접 구현한 함수의 출력**을 기대값으로 썼다. 외부 기준과는 비교하지 않았다.
5. **왜 릴리스 전에 못 잡았나?** → 릴리스 체크리스트에 외부 라이브러리 결과와 비교하는 통합 검증 단계가 없었다.

**근본 원인**: 같은 계산이 두 곳에 중복 구현되어 있었고, 테스트는 자기 코드의 출력하고만 비교했다.

## How — 어떻게 고치고 막을 것인가
**즉시 조치 (완료)**
- `_std()`를 지우고, 표본 표준편차(ddof=1)를 계산하는 `descriptive.std()`를 가져다 쓰도록 바꿨다.
- 모든 검정 함수에 `scipy.stats` 결과와 비교하는 테스트를 추가했다.
- v0.1.1을 릴리스하고, 릴리스 노트에 영향 범위를 적었다.

**재발 방지**
| 할 일 | 담당 | 기한 |
|---|---|---|
| `descriptive` 모듈 밖에서는 `np.var` / `np.std`를 직접 호출하지 못하게 막는 ruff 규칙 추가 | 개발 | 11/27 |
| 릴리스 체크리스트에 "외부 라이브러리 비교 테스트 통과" 추가 | 개발 | 11/25 |
| PR 템플릿에 "버그를 고치면 같은 패턴을 코드 전체에서 검색" 단계 추가 | 개발 | 11/25 |

## 배운 점
- 버그를 고치면 **같은 패턴이 다른 곳에도 있는지** 반드시 찾아본다 (`grep -rn "np.std\|np.var" src/`).
- 테스트의 기대값은 직접 구현한 코드가 아니라 **독립된 기준**(scipy, statsmodels, 손계산)에서 가져온다.
